01

三件工具的分工

VS Code、PyCharm、Trae 不是三选一，而是三种角色。先把角色分清，就不会在"装哪个插件、在哪写代码"上反复纠结。

工具它是什么在你手里的用途
VS Code 微软的开源编辑器，插件生态最大 当作"干净的地基"：装 Python、Stata 语法高亮、Markdown、Git。Trae 就是它的深度定制版，两者界面几乎一样。
PyCharm JetBrains 的 Python 专用 IDE 只在"大型 Python 项目重构、调试断点"时用。写论文脚本、跑 Stata 时它太重，且对 Stata 几乎没有支持。
Trae CN VS Code 内核 + 中文 AI 助手 + SOLO 工作台 日常主力。它能直接读你的整个项目、在终端跑命令、跨多个文件改代码，还能把"跑一遍看看"这件事自己完成。

一句话结论：把 Trae 设为默认打开方式；VS Code 留着当备用和插件试验田；PyCharm 只在你需要重型 Python 工程时打开。

三者的设置基本互通：Trae 首次启动可以导入 VS Code 的配置、快捷键与插件。

为什么 Trae 对你是"变革"而不是"又一个编辑器"

  • 它看得见上下文。你打开的是整个 trae-guide 文件夹，它就知道 02_did.do 依赖 01_clean.do 产出的 .dta，不用你解释。
  • 它能动手。不只是给代码片段，而是直接写进文件、在终端执行、读报错、再改。
  • 它把"我不知道这个命令怎么写"变成了"我说清楚要什么"。对非法学/非计算机出身的人，这是最大的门槛削减。
02

十分钟上手 Trae

不求学完所有功能，只求把"打开项目 → 提需求 → 看它改 → 自己验证"这条闭环走通一遍。

第一步：打开文件夹，而不是打开文件

菜单 文件 → 打开文件夹，选 trae-guide。这一步决定了 AI 的视野：只开一个文件时，它只能看见那一个文件；开了文件夹，它才能看到 data/、output/、run_all.do 之间的关系。

新手最常见的错误：双击某个 .py 打开，然后问"为什么它说找不到模块"。因为工作目录不对——终端要在项目根目录里跑。

第二步：认准四块界面

左侧：资源管理器

文件树。点一下文件名就在中间打开。下面还有搜索（全局找关键词）、源代码管理（Git 改动）。

中间：编辑器

写代码、看日志、看 Markdown。顶部标签页可以同时开很多个文件。

下方：终端

Ctrl + ` 呼出。你所有的 python xxx.py、Stata 批处理都在这里跑。

右侧：AI 面板

提问、让它改代码的地方。顶部一般有模式切换（Chat / Builder / SOLO）。

第三步：五个必须记住的快捷键

快捷键作用什么时候用
Ctrl + P按文件名快速跳转项目文件多的时候，比在树里点快十倍
Ctrl + `显示／隐藏终端跑脚本、看报错
Ctrl + Shift + P命令面板找不到某个功能时，直接搜中文/英文关键词
Ctrl + I内联编辑（选中代码后）只改几行时，比开侧栏对话更精准
Ctrl + S / Ctrl + Z保存 / 撤销AI 改坏了就撤销，别慌

第四步：确认你的运行环境

在终端里敲 python -V，应看到 Python 3.11.7。如果版本不对或提示找不到命令，按 Ctrl+Shift+P，搜 Python: Select Interpreter，选 C:\Users\cheny\anaconda3\python.exe。

Stata 不走插件，走命令行批处理（StataMP-64.exe /e do run_all.do）。本机已写好 run_stata.ps1：它会自动找到 Stata 安装位置、把工作目录切到脚本所在目录，再用 -Wait 等它真正跑完。你只要在终端执行 .\run_stata.ps1。

自动探测失败（绿色版、装在非标准目录）时，脚本会提示你：把文件开头的 $stata = $null 改成实际路径，或先执行 $env:STATA_EXE = "你的路径"。

记住这句话：AI 负责写和改，终端负责证明它真的能跑。任何"应该可以"都不算完成。

03

四个用法档位

同一个 AI，用在四个不同"档位"上，效果差很多。选错档位，要么大炮打蚊子，要么让它在没看懂项目时乱改一通。

档位你在做什么你需要提供典型风险
① Chat
问答		 问概念、让它解释一段看不懂的代码、把报错贴给它 问题 + 相关代码／报错原文 它可能没读你的项目就回答，结论泛泛
② Ctrl+I
内联		 选中 3–20 行，说"把这里改成……" 选中的代码 + 明确的改法 选多了它会顺手改你没让它改的地方
③ Builder
智能体		 给一个目标，让它跨多个文件改，并自己跑命令验证 目标 + 边界（只改哪些文件）+ 验收方式 改动面大，不看 diff 就点接受会很难回退
④ Rules + MCP
长期配置		 把"我的写作规范／数据路径／禁用操作"写进规则文件；接入外部数据源 一次性写清规则，之后自动生效 规则写得太模糊等于没写；MCP 会带来外部访问

建议的进阶顺序

先用一周档位 ① 和 ②，把"描述需求"练顺；再开档位 ③ 处理多文件任务；最后才写 Rules。一上来就用 ③，你还没有能力判断它改得对不对。

一个判断口诀

能一句话说清"改成什么" → 用 ②；只能说清"要达成什么" → 用 ③；只是想知道"为什么" → 用 ①。

04

SOLO 模式：什么时候用，什么时候别用

SOLO 不是"更强的 Chat"，而是另一种工作形态——它把 AI 从"坐在你旁边的顾问"变成"接手整件事的承包人"。理解这一点，比记住任何按钮位置都重要。

它到底哪里不一样

普通模式里，你是操作者：你选文件、你跑命令、AI 给你建议或改好代码，你再验证。SOLO 里，你只交目标，它自己排计划、自己动手、自己验收，你退到"审阅者"的位置。

左：会话你和它对话、补充约束
中：计划 · 执行流待办清单逐项推进，每步有状态
右：预览 / 终端它跑的命令、起的服务、看到的画面

不同版本的入口与布局略有差异，通常在 AI 面板顶部的模式选择器里，或侧栏的 SOLO 图标。第一次进入会新建一个任务工作台。

维度普通模式（Chat / Builder）SOLO 模式
形态编辑器 + 侧栏对话，你是操作者任务工作台：会话、计划执行流、预览终端三栏并列
交互单位一句一问一答，围绕你选中的代码交一个目标，它先出 Plan 与待办清单，再逐项执行
能力边界在编辑器内读写文件、跑终端命令可以接管编辑器之外的整机操作（Computer Use、录屏回放、IM 桥接）
交付给你改好的代码，跑不跑取决于你端到端：装依赖、跑脚本、起服务、用内置浏览器验收、失败自修复
风险模型误改一两个文件，撤销即可误动目录、误装全局包、误操作别的窗口；权限确认更密，你必须看 diff

什么时候用它

① 搭新项目骨架

"建一个 Stata 实证项目：数据生成脚本、清洗 do、主回归 do、稳健性 do、一键运行脚本，目录分 data/output。" 这种从零到能跑的结构，正是它的强项。

② 端到端的小流程

"装依赖 → 跑脚本 → 报错就改 → 直到产出 CSV。" 你不用在报错和修改之间来回搬运，它自己闭环。

③ 批量、多文件的机械改动

"把 12 个脚本里的 utf-8 全部改成 utf-8-sig，并统一输出文件名。" 逐文件点开改会疯，交给它更稳。

④ 你暂时离开电脑

"我去开组会，你把这三份判决的要素表做出来，做完把结果放 output/ 并写个 README 说明。" 回来后你审阅，而不是从零开始。

什么时候别用它

① 未脱敏的当事人／企业数据

它能操作整机、能截屏、能读其他窗口。涉密卷宗、委托人信息、未公开的微观企业数据，不要放进 SOLO 工作台。先在只读副本上脱敏，再谈自动化。

② 需要精确复现的实证结果

论文表格必须你能解释每一个系数。让 SOLO 自己决定回归设定、自己判断显著性，你会在答辩时答不上来。实证请用普通模式改代码，自己看 log。

③ 法条与案号的核验

这类核验的正确答案只能来自官方文本。SOLO 再"自主"，也不能替代你打开国家法律法规数据库逐条对。它只能帮你缩小核对范围。

④ 只改一行代码

为了一个变量名进 SOLO，等于请工程队来拧一颗螺丝。选中那行按 Ctrl+I 就够了。

推荐工作流：起草归它，定稿归你

SOLO 起草骨架与流程→ 普通模式逐段精修→ pytest / Stata log 回归验证→ 你签字（写进论文／文书）

SOLO 的产出永远定位为"初稿"。它的价值是把你从搭建和搬运里解放出来，不是替你做判断。

在 SOLO 里必须坚持的三条纪律

  1. 先让它出 Plan，你逐条删改后再放行。计划阶段改一句话，比执行完再回滚十个文件便宜得多。
  2. 开工前声明数据边界。原话可以是："data/ 目录只读，任何产物写到 output/，禁止修改或删除原始文件。"
  3. 每完成一步要一次回执。"把这一步改了哪些文件列出来，并给我 git diff。" 没有 diff 的"已完成"不算完成。

切换模式时的实际问题：不同会话之间的上下文不共享。切回普通模式前，把结论落到文件里（比如 NOTES.md），而不是指望它记得另一个窗口说过什么。

提示词四件套

你不需要学"提示词工程"，只需要每次把四件事说清楚：角色、目标、约束、验收。缺哪一件，它就会在哪一件上自由发挥。

要素回答什么问题例句
角色你希望它站在谁的角度你是熟悉 Stata 18 与因果推断的实证研究者
目标最终要得到什么产物把 02_did.do 改成三列递进回归并导出表格
约束不许做什么、必须遵守什么不改数据清洗逻辑；不加新依赖；只动这一个文件
验收怎样算成功跑完 log 里三列都输出，且 output/tab_did.rtf 存在
可直接复制的模板
你是【角色】。请【目标】。
约束：1) 【不许做什么】；2) 【必须遵守什么】；3) 只改【文件范围】。
验收标准：【可观察的结果】。
动手前先读相关文件，列出你打算改哪些文件，等我确认再改。

反例：为什么"帮我看看这个代码"没有用

差 帮我优化一下这个脚本

它不知道"优化"指速度、可读性还是结果正确性，于是会大改结构、引入不存在的包，你还不好意思拒绝。

好 这个脚本跑 3000 行要 4 分钟

请只改 parse_local.py 里 dedupe() 的实现，把 O(n²) 换成集合去重；不改输出列名与顺序；改完告诉我怎么用同一份 fixtures 验证结果条数不变。

三句万能补充

  • "先读文件再动手，不要凭猜测写代码。"
  • "改动前列出你要改的文件和理由。"
  • "改完告诉我怎么验证，并给出验证命令。"

场景一：Stata 科研实证

目标不是"让 AI 写个回归"，而是"让 AI 帮你把一条可复现的实证流水线搭起来，并且每一段你都能讲清楚"。

00 生成／导入数据→ 01 清洗 · 缩尾 · 声明面板→ 02 双向固定效应 DID→ 03 稳健性 · 事件研究 · 安慰剂→ 导出表格
文件作用
00_make_data.py生成 300 家企业 × 2010–2020 的合成面板（固定随机种子，可复现），输出 data/panel.csv
01_clean.doimport delimited、destring、isid 查重、xtset 声明面板；按年做 1%/99% 缩尾，存 data/panel_clean.dta
02_did.do三列递进回归：xtreg esg did, fe → 加控制变量 → 加年份固定效应，聚类到 city_code，estimates table 输出，并尝试 esttab 导出 RTF
03_robust.do换聚类层级、事件研究（以 rel = -1 为基期）、安慰剂（把政策时点提前到 2013，只用 ≤2014 样本）
run_all.do / run_stata.ps1依次执行三步；PowerShell 脚本负责调起 StataMP-64.exe /e do run_all.do，日志落到 run_all.log

本机实际跑出来的结果：三列模型中 did 系数均为 0.179，在 1% 水平显著；事件研究可看平行趋势；安慰剂检验 fake_did = 0.006，不显著——说明主结果是"真政策"带来的，而不是趋势。

这些数字来自合成数据，只用于演示流程，不能写进论文。

用 Trae 做实证的正确姿势

  1. 先让它读，不让它写。"读 01_clean.do 和 02_did.do，用中文解释每一步在干什么、为什么这样设定。"
  2. 再让它改一处。用 Ctrl+I 选中聚类那一行，说"把聚类层级从 city_code 换成 industry_code"。
  3. 每次都自己看 log。AI 说"跑通了"不算，run_all.log 里出现 r(198)、r(111) 这类错误码就是没跑通。

场景二：数据爬取

爬虫的正确入门顺序是"先解析本地快照，再请求真实接口"。顺序反了，你会在网络错误和选择器错误之间反复怀疑人生。

第一级：本地 HTML 解析

parse_local.py 读 fixtures/page1.html 与 page2.html，用 BeautifulSoup 抓列表，按案号去重，写 output/cases_from_html.csv。

实测：第 1 页 5 条 + 第 2 页 5 条，第 2 页故意重复 1 条 → 去重后 9 条。

第二级：真实开放接口

fetch_macro.py 调世界银行 Open Data API，抓 GDP、人均 GDP、城镇化率、失业率（2005–2023），带分页、3 次重试、0.5 秒限速。

实测：4 个指标去空值后 76 条观测，并留了一份 output/raw/ 原始 JSON 快照。

合规红线（这一节请务必逐条读）

  • 先看规则：目标站点的 robots.txt 与用户协议。不许抓的，一行都别抓。
  • 限速：示例里每页 sleep 0.5 秒。把对方服务器压垮，性质就变了。
  • 不绕过：登录、验证码、付费墙、反爬机制，绕过即可能违法。
  • 只取公开、非敏感信息：涉及个人信息时，《个人信息保护法》《数据安全法》直接适用。
  • 留快照：原始返回存 raw/，既为了复现，也为了日后能说明"数据是哪天、从哪来"。

把 HTML 表格变成论文能用的数据

抓下来只是原料。pandas 读 CSV → 统一单位与缺失值标记 → 输出面板格式，这一段建议在普通模式里一步步做，每步都打印 df.shape 和 df.head()，确认形状没变。

场景三：法律案件对比

这个场景最危险，也最适合展示"AI 该怎么用"：它可以帮你把三份判决书的要素摆成一张表，但它说的每一条法条都必须回到官方文本核对。

extract.py 抽要素→ compare.py 横向对比 + 理由 diff→ check_citations.py 引注核验→ 你人工核对官方文本
文件产出与要点
extract.py正则抽取案号、法院、案由、裁判日期、诉请金额、援引法条、结果倾向 → output/elements.csv
compare.py生成要素横向对比表，并用 difflib 对 case_a 与 case_c 的【裁判理由】做差异，把"义务主体 / 相对人是否善意"的说理分岔标出来 → output/comparison.md
check_citations.py把判决书里的援引与 refs/law_articles.json 比对，输出"命中／未收录"两态清单

本机实测：3 份合成判决书（股东回购部分改判 / 公司回购因未减资被驳回 / 公司担保因相对人非善意改判），共 12 处援引，命中 11 处，未收录 1 处——《公司法》第一百四十二条（示例条文库故意未收，用来演示这一分支）。

"未收录"≠"引错"，只表示示例条文库没收这条。这正是工具的正确用法：缩小人工核对范围，而不是替代人工核对。

防幻觉三条

  1. 只认本地或官方文本。把条文放进 refs/ 或让它在国家法律法规数据库里检索；不接受"根据民法典第五百八十五条……"这种凭记忆生成的引注。
  2. 命中也只是第一步。还要确认：法律名称是否现行有效、条文序号是否因修法变动、引用内容是否与条文原意一致。
  3. AI 生成的法条与案号一律标"待核验"。在你逐条核对完之前，不许出现在正文里。

场景四：改 Python 代码

这是最适合练手的场景，因为它有客观的验收标准：9 个单元测试。红变绿，就是改对了。你不需要看懂全部代码，也能判断它有没有真的修好。

位置埋的坑症状
normalize_case_no()全角转半角的映射方向写反了案号里的括号怎么都规整不了
char_bigrams()取的是单字集合，不是二元组相似度算出来虚高
jaccard()分母用了 len(sa) 而非并集结果恒为 1 或明显偏大
extract_amount()正则不认千分位逗号与"万元"120 万被判成 120
summarize_judgments()空列表直接除零批量跑时突然崩在最后一批

本机实测：python -m pytest -q → 5 failed, 4 passed；直接 python case_utils.py 会在最后抛 ZeroDivisionError。目标是把 9 个测试全部变成绿。

四步修法（不要让它一次性全改）

  1. 先跑测试，看红在哪。把失败输出整段贴给它，让它解释每个失败对应哪个函数。
  2. 一次只修一个函数。选中那个函数按 Ctrl+I，说清"只改这个函数，不改测试"。
  3. 每改一次就跑测试。红数在减少才算进展；如果红数变多，立刻撤销。
  4. 全绿之后要求解释。"用中文说明这五处修改各自为什么能修好对应测试"，答不上来就说明你没真正掌握。
示例提示词：带着测试改代码
你是 Python 工程师。tests/test_case_utils.py 是我的验收标准，不许修改测试文件。
请只改 case_utils.py，一次只修一个函数，
每次改完告诉我跑哪条命令验证、预期几个测试转绿。
如果我的测试本身写错了，先告诉我，不要擅自改测试来迁就代码。

边界与纪律

工具的上限由能力决定，下限由纪律决定。下面这些不是"注意事项"，而是会直接影响你论文与执业风险的红线。

它会编，而且编得很像

法条序号、案号、统计口径、API 参数，都可能凭空生成。凡是"事实性"内容，一律要求给出处，并自己核。

数据不要随手扔进去

未脱敏的卷宗、当事人信息、未公开的企业微观数据，不进 AI 上下文。先脱敏，或只给结构描述。

原始数据只读

所有脚本只读 data/，产物写 output/。这样最坏情况也只是重跑，不是重找数据。

可复现优先

固定随机种子、写 requirements.txt、记录 Stata 版本与命令。半年后你自己也要能重跑。

三个"别做"

  • 别在没看 diff 时点"接受全部"。改动面越大，越要逐个文件看——你签的是自己的名字。
  • 别让 AI 直接改原始数据文件。包括 .dta、.csv、判决书原件。只让它改脚本。
  • 别把"它说跑通了"当成跑通了。你要亲眼看终端输出、log 结尾、产物文件是否存在。

关于 Stata 的一个具体提醒：AI 很容易写出 egen pctile() 这种"看起来对但 Stata 没有"的命令。凡是它给的 Stata 代码，先看 log 里有没有 command … is unrecognized，再决定信不信。
